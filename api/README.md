# API-тестирование формы заказа (EmailJS)

## Цель
Проверить, как API обрабатывает данные формы заказа, и сравнить с поведением UI.

## Инструменты
- **DevTools** (перехват запроса в браузере)
- **Postman** (отправка запросов к API)

---

## Структура запроса

**Метод:** `POST`  
**URL:** `https://api.emailjs.com/api/v1.0/email/send`  
**Заголовки:** `Content-Type: application/json`

**Тело запроса (пример):**
```json
{
  "lib_version": "3.2.0",
  "user_id": "user_xxx",
  "service_id": "service_xxx",
  "template_id": "template_xxx",
  "template_params": {
    "name": "Лена",
    "email": "ad@mail.ru",
    "product": "Видеокарта",
    "quantity": "3",
    "date": "2026-08-29",
    "need": "нет"
  }
}
```

> **Примечание:** ключи `user_id`, `service_id`, `template_id` — тестовые заглушки, поэтому все запросы возвращают `400 Bad Request`. Это не мешает проверить валидацию полей.

---

## Проведённые проверки

| Сценарий | Изменение в теле запроса | Код ответа | Результат |
|----------|--------------------------|------------|-----------|
| Валидные данные | Без изменений | `400` | Заглушки, ожидаемо |
| Невалидный email | `"email": "shjsh@ff.rf"` | `400` | ✅ API блокирует невалидный email |
| Пустой email | `"email": ""` | `400` | ✅ API требует заполнения |

---

## Выводы

1. **API корректно валидирует email** — на невалидный адрес (`shjsh@ff.rf`) сервер возвращает `400 Bad Request`.  
2. **В UI такой адрес принимается** — это подтверждает **BUG-05** (неполная валидация на фронтенде).  
3. **Бэкенд работает надёжнее фронтенда** — проблема только в клиентской части.  
4. **Рекомендация:** усилить валидацию на стороне клиента, чтобы форма не отправляла невалидные данные даже до запроса к API.
